# Testing and regression expectations

Prefer public, observable behavior:

- `mask()` returns the same input, whose non-enumerable `secretInput` Symbol property exposes the stable state; no string property is added.
- `input[secretInput].value` holds the actual value. `input.value` contains bullets by default and contains the same actual string only after explicit reveal.
- Switching `redacted` is quiet, preserves logical selections across UTF-16/grapheme offsets, and does not change secret or history.
- Insert, paste/drop, selection replacement, delete, keyboard and `beforeinput` undo/redo, composition, and grapheme edits update the right actual range. Contiguous typing and character deletion form one history transaction, while caret/pointer movement and unrelated edits start a new one. Composition drafts remain outside the actual state, and Safari-style commit-before-end ordering commits exactly once.
- Copy, cut, and selection dragging cannot export either the secret or masks while redacted; revealed state restores native export and cut behavior. The native context menu remains available.
- Unexpected `input.value` mutations never enter secret state in either presentation.
- `FormData` receives actual values; disabled controls are omitted and reset restores the state `defaultValue`.
- React controlled values and Vue `v-model` receive actual edits while their rendered native values remain presentation state; accepted values preserve undo history, browser-written values do not reach adapter callbacks, and both adapters forward input attributes and preserve form participation.
- Property writes are quiet; user edits emit `input`, and blur after editing emits `change`.
- Masking the same input repeatedly is idempotent.
- The Chromium custom-password primer is written before the authoritative mask and never remains as the visible value of an empty or one-grapheme secret.

Happy DOM tests establish fast invariants, not engine interoperability. Before release, test current Chrome, Edge, Firefox, Safari, and iOS Safari with software/hardware keyboards, selection handles, paste/cut, autofill, Japanese and Chinese IMEs, combining marks, emoji, and the assistive-technology matrix. In Chromium-based browsers, verify whether an empty primed field suppresses IME switching before the first edit without triggering password autofill.

The root comparison page starts with a conventional Username + Password form using standard `name` and `autocomplete` metadata. Submit a disposable credential and accept the browser's save prompt before testing. Password-manager extensions must be disabled for the site so the setup and comparison measure the browser itself. The page watches for known extension DOM markers and blocks setup when it finds one, but the browser exposes no complete extension-enumeration API, so this remains a best-effort guard. The page stores only a completion flag in local storage; it never stores the credential values. The reset control clears that flag but cannot remove credentials from the browser's password manager.

Only after setup does the page insert four Webhook URL/Signing secret forms into the DOM. Their order follows the usual escalation: native password with `autocomplete="off"`, the common `autocomplete="new-password"` workaround, text with `-webkit-text-security: disc`, then `mask()` on text. The comparison matrix evaluates automatic fill separately from interaction-triggered autofill UI, then covers actual-value exposure to assistive technology, undo/redo, IME disabling, and native password accessibility. Every cell reports Chrome, Edge, Firefox, and Safari separately: full-color icons mean supported, an amber outline means best effort, and gray means unsupported. Each icon's title and its cell's accessible description explain the observed failure or the exact best-effort boundary. This distinction separates browser-dependent behavior from approximations that work everywhere but are not fully native. Safari is supported for avoiding automatic fill in the observed cases but unsupported where focus still opens password UI. Each interactive case briefly explains why the approach is used and where it fails. The non-login webhook example avoids implying that the component is specific to OAuth clients. All Webhook URL fields are plain text inputs so URL-specific browser behavior does not affect the comparison. The CSS experiment must call `CSS.supports()` before applying the property. The comparison fields intentionally omit `name`; all fields use `autocomplete="off"` except the second native secret, whose `new-password` token is the variable under test. Both text-secret cases request `ime-mode: disabled`, cancel `compositionstart` when possible, and disable autocapitalization, autocorrection, and spellcheck. Never enter real credentials there. Use the page for saved-credential autofill, password-manager, context-menu, IME, and assistive-technology comparisons.
