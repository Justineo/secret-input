# Testing and regression expectations

Test useful input capabilities and the documented component contract. Do not treat every difference from a raw native input or every form-library integration style as a defect. DOM plaintext isolation is not a product goal.

Prefer public, observable behavior:

- `createSecretInput()` returns a controller distinct from its input, with read-only state and synchronous update patches. Native elements have no secret properties or method overrides.
- `controller.value` holds the actual value. `input.value` contains bullets by default and contains the same actual string only after explicit reveal.
- Switching `revealed` is quiet, preserves logical selections across UTF-16/grapheme offsets, and does not change secret or history.
- Insert, paste/drop, selection replacement, delete, keyboard and `beforeinput` undo/redo, composition, and grapheme edits update the right actual range. Contiguous typing and character deletion form one history transaction, while caret/pointer movement and unrelated edits start a new one. Composition drafts remain outside both the actual state and the restored DOM presentation, and Safari-style commit-before-end ordering commits exactly once.
- Copy, cut, and selection dragging cannot export either the secret or masks while redacted; revealed state restores native export and cut behavior. The native context menu remains available.
- Unexpected `input.value` mutations never enter secret state in either presentation.
- `createSecretInput()` enforces `autocomplete="off"` and the known vendor opt-out attributes; React and Vue render the same attributes before attaching the controller.
- `FormData` receives actual values in browser entry order while preserving ordinary same-name inputs, textareas, selected options, and files. Submitters and dirname entries use distinct names. Disabled controls are omitted and reset restores the state `defaultValue`.
- React value/onChange(value: string) and Vue defineModel receive actual edits while DOM values remain presentation. React callbacks receive the string directly and accept a state setter; Vue reports update:modelValue. Accepted values preserve undo history, rejected values restore parent state, and browser-written values do not reach ordinary adapter callbacks. React uncontrolled reset restores defaultValue; React controlled and Vue model resets preserve the current model unless the parent updates it. Verify cancelable resets, callback refs/Strict Mode, and attribute updates without selection loss.
- React and Vue server output contains the initial grapheme-length bullets with autofill and text-service defaults, never plaintext; the readonly guard prevents actual keyboard editing before hydration, attachment restores the author's readonly state, and pre-hydration script/browser writes are discarded.
- Controller updates are quiet; user edits emit `input`, and Enter or blur emits `change` only for a user-edited value that differs from the last confirmation, focus, or reset baseline. Repeated Enter, blur after confirmation, and undo back to the baseline do not emit another `change`. Enter must retain focus and allow implicit submission, with change-driven validity updates before browser validation. Keydown cancellation must prevent both confirmation and submission.
- Repeated creation returns the same controller without reinitialization. Explicit updates refresh form bindings after relocation.
- Splices that join neighboring graphemes retain the correct caret and undo grouping; reveal/redact preserves backward selections.
- Canceled transfers, missing insertion data, mismatched native input, and reentrant DOM events cannot overwrite secret state.
- Reaffirming a controlled value preserves the composition replacement range; reset and readonly/disabled transitions cannot commit stale drafts.
- Detached, shadow-root, and same-origin iframe forms submit actual values and reset correctly.
- The Chromium custom-password primer is written before the authoritative mask and never remains as the visible value of an empty or one-grapheme secret.

`tests/package` type-checks actual package exports with strict declaration checking after the library build. It covers React value-callback and ownership types plus a Vue v-model/ref consumer. Run `pnpm check:package-types`; do not substitute source imports or skipLibCheck, since those would miss invalid published type dependencies.

Happy DOM tests establish fast invariants. `vp run test:browser` uses Vite+'s Vitest Browser Mode with WebdriverIO to repeat the public contract in installed Chrome, Edge, Firefox, and real Safari: keyboard edits, Unicode and selections, UTF-16 `maxlength`, clipboard and context-menu events, undo/redo, both observed composition commit orders, direct DOM/autofill-shaped mutations, form data/reset (including real reset-button activation, late cancellation, and preserved history), native constraints, events, the masked DOM value, and accessible name/role. Select one with `BROWSER=chrome`, `edge`, `firefox`, or `safari`. Safari requires Allow Remote Automation or `safaridriver --enable`; CI enables it and runs all four targets independently.

The Chromium-only composition regression uses CDP `Input.imeSetComposition` and `Input.insertText` to exercise engine dispatch, native DOM mutation, original selection replacement, native required messages, and undo. This caught premature pending-edit expiration at native event microtask checkpoints. It is not an operating-system IME test; Firefox and Safari skip this CDP-specific case.

Browser automation uses isolated profiles, so it cannot provide a durable saved-credential autofill test. The browser suite instead covers both relevant mutation shapes: rejected `insertReplacementText` and a value write followed by `input`. Keep saved-credential autofill, real IMEs, iOS selection handles, and the assistive-technology matrix as manual release tests. In Chromium-based browsers, also verify whether an empty primed field suppresses IME switching before the first edit without triggering password autofill.

The CI workflow is also reusable by the release workflow. Its package job runs static and Vue checks, unit tests, both builds, and `publint`; its independent browser jobs cover Chrome, Edge, Firefox, and Safari using the matching drivers already installed on the pinned runner images. Main-branch deployment and tagged release publishing must wait for the entire workflow, and browser failures upload diagnostics. Keep permissions scoped to the deployment and publishing jobs.

The home page presents its product explanation and usage example in static HTML. Its browser experiment starts with a conventional Username + Password form using standard `name` and `autocomplete` metadata. Submit a disposable credential and accept the browser's save prompt before testing. Password-manager extensions must be disabled for the site so the setup and comparison measure the browser itself. The page watches for known extension DOM markers and blocks setup when it finds one, but the browser exposes no complete extension-enumeration API, so this remains a best-effort guard. The page stores only a completion flag in local storage and never stores the credential values. The native submit event is canceled so no credentials are posted. After the comparison module is ready, submission removes the setup form and calls `history.replaceState()` with `#compare` as a same-document login-completion signal. The persistent page shell and fonts stay in place. Reset clears the flag and renders setup in the same document, but cannot remove credentials from the browser’s password manager. Focus moves to the new stage heading without forcing a scroll.

Only after setup does the page insert five Webhook URL/Signing secret forms into the DOM. Their order follows the usual escalation: native password with `autocomplete="off"`, the common `autocomplete="new-password"` workaround, text with `-webkit-text-security: disc`, an experimental one-row textarea with the same CSS mask, then `createSecretInput()` on text. The comparison matrix evaluates automatic fill separately from interaction-triggered autofill UI, then covers actual-value exposure to assistive technology, undo/redo, IME disabling, and native password accessibility. Every cell reports Chrome, Edge, Firefox, and Safari separately: full-color icons mean supported, an amber outline means best effort, gray means unsupported, and a dashed outline means not tested. Each icon’s accessible name identifies the browser and support level. Its title gives the assessment. Focusing or selecting an icon highlights it and shows only its assessment notes as plain text below the table, including on touch devices. This distinction separates browser-dependent behavior from approximations that work everywhere but are not fully native. Safari is supported for avoiding automatic fill in the observed cases but unsupported where focus still opens password UI. Each interactive case lists its input type and configuration, explains why the approach is used, and summarizes its limitations. Keep the distinction between the intended effect and observed browser behavior explicit. The matrix provides per-browser details. The non-login webhook example avoids implying that the component is specific to OAuth clients. All Webhook URL fields are plain text inputs so URL-specific browser behavior does not affect the comparison. The CSS experiment must call `CSS.supports()` before applying the property. The comparison fields intentionally omit `name`; all fields use `autocomplete="off"` except the second native secret, whose `new-password` token is the variable under test. Both text-secret cases request `ime-mode: disabled`, cancel `compositionstart` when possible, and disable autocapitalization, autocorrection, and spellcheck. Never enter real credentials there. Use the page for saved-credential autofill, password-manager, context-menu, IME, and assistive-technology comparisons.

`tests/history.test.ts` exercises history through the public input surface: stable before/after selections over repeated undo/redo, collapsed-edit grouping versus range edits, branching, no-ops, composition isolation, pending-input invalidation, disabled/readonly states, external replacements and reset, changed length limits, reveal transitions, selection notifications, reentrant callbacks, and full backward/forward traversal of independent Unicode edits. React and Vue tests cover redo surviving controlled synchronization and being discarded by a new branch. `tests/browser/history.test.ts` adds real keyboard shortcuts, real typing/deletion groups, native selection events, non-cancelable input ordering, and event payload/blur checks. Keep these tests behavioral; history internals remain private.

Write compatibility notes in terms of observable behavior, using the same wording across browsers and solutions when the outcome is equivalent. Call out differences only when they affect use, such as which fields show password suggestions, whether IME remains available, or how undo behaves. Keep platform accessibility identifiers, event names, CSS mechanisms, and initialization techniques in the technical documentation rather than the table.

Vite highlights the plain JavaScript example in `index.html` with Shiki during HTML transformation in development and production. The generated tokens use light/dark CSS variables; no Shiki runtime, grammar, or WASM is sent to the browser.

The home page uses native scrolling and keeps its critical CSS inline in the production HTML; development uses a normal head stylesheet. Only the small setup entry loads on a first visit. Focusing the setup form warms the comparison module and stylesheet without inserting comparison inputs. A completed visit loads that module immediately. Submission keeps the filled setup form visible and disables duplicate submits until loading finishes, then checks the extension guard and writes the completion flag before switching stages. A failed import or storage write leaves the setup values intact and does not mark setup complete. An initial comparison load failure keeps the existing flag and offers an explicit reload action because failed module loads can be cached. Successful setup and reset must never reload the document. Fonts are self-hosted, with the primary face preloaded and optional font display. The code font is a regular-weight ASCII/bullet subset of Geist Mono, with its source and license documented in `public/fonts/`. Keep the light/dark color-scheme metadata before styles so the initial canvas matches the system theme.

Verify cold loads against the production build, including disabled JavaScript, blocked deferred requests, and 320px, 390px, tablet, and desktop widths in both themes. Check the actual viewport width as well as document overflow, since a wide element can expand a mobile layout viewport. Horizontal overflow belongs inside the keyboard-focusable compatibility region. Storage denial must leave setup usable and prevent credential submission, with a visible explanation when its completion flag cannot be written. `tests/demo.test.ts` covers static content, storage failures, deferred-module failure, the extension guard, and keyboard/click access to matrix details. For the saved-stage startup path, wait for the observable `aria-busy="false"` state before inspecting the completed UI; module evaluation alone does not establish that the startup render has finished. It also checks repeated setup/reset cycles, stable shell nodes, heading focus, and extension detection while the comparison is loading. Production diagnostics verify that switching stages preserves `performance.timeOrigin`, creates no document or font requests, and keeps the hero’s dimensions unchanged. `vp run check:site` runs after the site build in CI to enforce initial HTML/JavaScript/font budgets and catch accidental eager loading of comparison assets. The library build and website build share `dist`; run the site check after `vp build`, not after `vp pack`.

Validation regression coverage must include synchronous patches, omitted keys versus explicit undefined, dynamic framework prop additions/replacement/removal, Unicode lengths, optional emptiness, native required messages, reset, native disabled/readonly exemptions, submission blocking, and preserved node/selection/history. Verify that the controller never extends input state or overrides setCustomValidity, and that no DOM rule migration or observation is required. Application customValidity persists through edits, history, same-value synchronization, reveal, reset, and unrelated React/Vue renders. Removing the prop or explicitly clearing the option exposes remaining rule errors. Native methods remain unmodified; direct native writes are not a separate managed error source. Check disabled/readonly/fieldset exemptions without losing stored errors, SSR prop consumption, and probe cleanup/reuse across value, rule, message-context, and owner-document changes. Invalid length configuration must reject the whole patch before state changes. Message-map overrides for all four supported failures must accept strings and synchronous formatters, update independently, fall back on empty/undefined entries or results and formatter exceptions without interrupting edits, history, reset, or native submission blocking, preserve rule enforcement and application-error priority, disappear when the rule passes, and stay out of DOM/SSR output. Verify formatter context, native required/pattern default wording, refreshing formatter closures without rewriting cached probe values, and replacement rather than merging of maps. Length-only checks must not create or write a detached validator.

The textarea candidate is comparison-only; it does not change the package controller or adapters.
It uses native value and history, `rows="1"`, `wrap="off"`, and horizontal caret scrolling.
Its small adapter blocks cancelable line-break edits and rejects multiline paste/drop without
rewriting the value. Plain Enter and cancelable line-break `beforeinput` from software keyboards call the test form's
`requestSubmit()`; composition confirmation
and modified Enter do not submit. The shared comparison handler cancels navigation, as for all
other candidates. This is not a complete single-line input implementation: non-cancelable edits,
programmatic newlines, and real OS composition still require investigation. Do not add native
password/IME priming or vendor ignore attributes to this candidate before measuring the basic
combination. Keep it read-only if CSS masking is unsupported. Autofill and password suggestions
remain explicitly untested until measured with saved credentials, especially in Safari. See
[the experiment report](../textarea-experiment.md) for results and manual verification steps.
