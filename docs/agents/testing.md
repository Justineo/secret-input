# Testing and regression expectations

Prefer public, observable behavior:

- `mask()` returns the same input with non-enumerable `secretValue`, `defaultSecretValue`, and `redacted` accessors.
- `input.secretValue` holds the actual value. `input.value` contains bullets by default and contains the same actual string only after explicit reveal.
- Switching `redacted` is quiet, preserves logical selections across UTF-16/grapheme offsets, and does not change secret or history.
- Insert, paste/drop, selection replacement, delete, keyboard and `beforeinput` undo/redo, composition, and grapheme edits update the right actual range. Contiguous typing and character deletion form one history transaction, while caret/pointer movement and unrelated edits start a new one. Composition drafts remain outside the actual state, and Safari-style commit-before-end ordering commits exactly once.
- Copy, cut, and selection dragging cannot export either the secret or masks while redacted; revealed state restores native export and cut behavior. The native context menu remains available.
- Unexpected `input.value` mutations never enter secret state in either presentation.
- `mask()` enforces `autocomplete="off"` and the known vendor opt-out attributes; React and Vue render the same attributes before attaching the controller.
- `FormData` receives actual values; disabled controls are omitted and reset restores the state `defaultValue`.
- React controlled values and Vue `v-model` receive actual edits while their rendered native values remain presentation state; accepted values preserve undo history, browser-written values do not reach adapter callbacks, and both adapters forward input attributes and preserve form participation.
- React and Vue server output contains the initial grapheme-length bullets with autofill and text-service defaults, never plaintext; attachment discards pre-hydration DOM mutations.
- Property writes are quiet; user edits emit `input`, and blur emits `change` only for a user-edited value that differs from the focus/reset baseline. Undo back to that baseline does not emit `change`.
- Masking the same input repeatedly is idempotent and refreshes form bindings after relocation.
- Splices that join neighboring graphemes retain the correct caret and undo grouping; reveal/redact preserves backward selections.
- Canceled transfers, missing insertion data, mismatched native input, and reentrant DOM events cannot overwrite secret state.
- Reaffirming a controlled value preserves IME drafts; reset and readonly/disabled transitions cannot commit stale drafts.
- Detached, shadow-root, and same-origin iframe forms submit actual values and reset correctly.
- The Chromium custom-password primer is written before the authoritative mask and never remains as the visible value of an empty or one-grapheme secret.

Happy DOM tests establish fast invariants. `vp run test:browser` uses Vite+'s Vitest Browser Mode with WebdriverIO to repeat the public contract in installed Chrome, Edge, Firefox, and real Safari: keyboard edits, Unicode and selections, UTF-16 `maxlength`, clipboard and context-menu events, undo/redo, both observed composition commit orders, direct DOM/autofill-shaped mutations, form data/reset, native constraints, events, the masked DOM value, and accessible name/role. Select one with `BROWSER=chrome`, `edge`, `firefox`, or `safari`. Safari requires Allow Remote Automation or `safaridriver --enable`; CI enables it and runs all four targets independently.

Browser automation uses isolated profiles, so it cannot provide a durable saved-credential autofill test. The browser suite instead covers both relevant mutation shapes: rejected `insertReplacementText` and a value write followed by `input`. Keep saved-credential autofill, real IMEs, iOS selection handles, and the assistive-technology matrix as manual release tests. In Chromium-based browsers, also verify whether an empty primed field suppresses IME switching before the first edit without triggering password autofill.

The CI workflow is also reusable by the release workflow. Its package job runs static and Vue checks, unit tests, both builds, and `publint`; its independent browser jobs cover Chrome, Edge, Firefox, and Safari using the matching drivers already installed on the pinned runner images. Main-branch deployment and tagged release publishing must wait for the entire workflow, and browser failures upload diagnostics. Keep permissions scoped to the deployment and publishing jobs.

The root comparison page starts with a conventional Username + Password form using standard `name` and `autocomplete` metadata. Submit a disposable credential and accept the browser's save prompt before testing. Password-manager extensions must be disabled for the site so the setup and comparison measure the browser itself. The page watches for known extension DOM markers and blocks setup when it finds one, but the browser exposes no complete extension-enumeration API, so this remains a best-effort guard. The page stores only a completion flag in local storage; it never stores the credential values. The reset control clears that flag but cannot remove credentials from the browser's password manager.

Only after setup does the page insert four Webhook URL/Signing secret forms into the DOM. Their order follows the usual escalation: native password with `autocomplete="off"`, the common `autocomplete="new-password"` workaround, text with `-webkit-text-security: disc`, then `mask()` on text. The comparison matrix evaluates automatic fill separately from interaction-triggered autofill UI, then covers actual-value exposure to assistive technology, undo/redo, IME disabling, and native password accessibility. Every cell reports Chrome, Edge, Firefox, and Safari separately: full-color icons mean supported, an amber outline means best effort, and gray means unsupported. Each icon's title and accessible name explain the observed failure or the exact best-effort boundary. Focusing or selecting an icon also shows the explanation below the table, including on touch devices. This distinction separates browser-dependent behavior from approximations that work everywhere but are not fully native. Safari is supported for avoiding automatic fill in the observed cases but unsupported where focus still opens password UI. Each interactive case briefly explains why the approach is used and where it fails. The non-login webhook example avoids implying that the component is specific to OAuth clients. All Webhook URL fields are plain text inputs so URL-specific browser behavior does not affect the comparison. The CSS experiment must call `CSS.supports()` before applying the property. The comparison fields intentionally omit `name`; all fields use `autocomplete="off"` except the second native secret, whose `new-password` token is the variable under test. Both text-secret cases request `ime-mode: disabled`, cancel `compositionstart` when possible, and disable autocapitalization, autocorrection, and spellcheck. Never enter real credentials there. Use the page for saved-credential autofill, password-manager, context-menu, IME, and assistive-technology comparisons.

`tests/history.test.ts` exercises history through the public input surface: stable before/after selections over repeated undo/redo, collapsed-edit grouping versus range edits, branching, no-ops, composition isolation, pending-input invalidation, disabled/readonly states, external replacements and reset, changed length limits, reveal transitions, selection notifications, reentrant callbacks, and full backward/forward traversal of independent Unicode edits. React and Vue tests cover redo surviving controlled synchronization and being discarded by a new branch. `tests/browser/history.test.ts` adds real keyboard shortcuts, real typing/deletion groups, native selection events, non-cancelable input ordering, and event payload/blur checks. Keep these tests behavioral; history internals remain private.

The demo loads both its base stylesheet and scrollbar stylesheet directly from the HTML head. Fonts are self-hosted, with the primary face preloaded and optional font display to avoid late swaps. Keep the light/dark color-scheme metadata before styles so the initial canvas matches the system theme. Verify cold loads against the production build, plus 320px, 390px, tablet, and desktop widths in both themes; horizontal overflow belongs inside the keyboard-focusable compatibility region. Storage denial must leave setup usable and prevent credential submission, with a visible explanation when its completion flag cannot be written. `tests/demo.test.ts` covers these storage failures and keyboard/click access to the matrix details.
