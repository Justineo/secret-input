# Browser, editing, and input methods

Support current Chromium, Firefox, and WebKit, including Safari and iOS Safari. The public editing surface stays native, while privacy requirements force the controller to replace browser value mutation for insertions.

Selections use logical grapheme positions inside the controller. Redacted DOM offsets map directly to those positions; revealed DOM selections use UTF-16 offsets and are translated at the boundary. `Intl.Segmenter` keeps surrogate pairs, combining sequences, and emoji ZWJ sequences atomic; the fallback is code-point based for non-browser embedding environments.

Native password inputs accept non-ASCII text, but their DOM selection and length contracts use UTF-16 code units, and major engines commonly render one mask per code unit. This controller deliberately uses one mask per extended grapheme instead: the presentation is already non-authoritative, and keeping each visible mask aligned with one editable unit prevents ordinary masked edits from splitting a valid Unicode sequence. Preserve the source string without Unicode normalization, apart from native single-line CR/LF removal. Enforce `maxlength` against source UTF-16 length, but truncate inserted text only between graphemes.

The controller cancels `compositionstart` when the browser permits it, approximating native password-field behavior. If composition still starts, keep its draft separate from the authoritative secret and commit it once from `insertFromComposition` or `compositionend`, whichever arrives first. This accommodates both Safari's commit-before-end ordering and Chromium variants that end composition without a separate commit event. Interim input events restore a length-matched mask without emitting a public `input` event or changing the actual state. If the engine never sends a commit event, the draft remains outside the secret and is discarded on blur.

Some engines expose IME edits as non-cancelable. While redacted, the browser may then place composition text in `input.value` after `beforeinput` and before the following `input` handler restores masks. Mutating the value while an IME owns a composition can itself disturb engine composition state, especially in WebKit. This is an unavoidable platform limitation of using a text input whose redacted DOM value must not retain plaintext; test actual input methods and document failures rather than adopting interim DOM text as secret state. Revealed mode intentionally displays the composition draft but still commits it to the actual state only once.

The controller sets the legacy `ime-mode: disabled` declaration as a Firefox-only hardening measure. Chromium and WebKit ignore it, so it is neither a cross-browser guarantee nor a substitute for composition handling.

Current Chromium also recognizes a text control that has contained at least two mask characters as a custom password field. During `mask()` initialization, the controller synchronously writes `••` and immediately replaces it with the authoritative presentation value before returning. Chromium retains the classification after the value changes and can use it to suppress IME context and apply password-oriented privacy protections. Never retain the two-character primer for an empty secret: doing so would break empty-value, placeholder, selection, validity, and accessibility behavior.

Current Chrome testing confirms that the primer prevents IME switching, so the comparison matrix marks Chrome as supported. The heuristic has no Web API or feature detection and is not a portable Chromium contract: current Edge does not reproduce that behavior, and it does not affect WebKit. In Edge and Safari, composition handling is the fallback—the IME remains available, but drafts do not change the actual state and the committed result is applied once. Retest IME switching, accessibility value announcements, and password autofill whenever browser versions change; the password manager may classify fields independently from the input-method layer.

Keep the browser's context menu. Its paste, delete, undo, and redo actions reach the controller through clipboard and `beforeinput` events when the browser dispatches them. Because canceling native edits and rendering masks does not populate the browser's private undo manager, also handle standard keyboard undo/redo shortcuts against secret-state history. Group contiguous typing and character deletion, and end the group for selection navigation, pointer interaction, composition, unrelated edit types, focus changes, and undo/redo.

History uses two stacks of transactions, each containing an explicit before and after snapshot of the secret and logical selection, including direction. Undo restores the transaction's original selection; redo restores its final caret. Traversal moves the same transaction between stacks, never samples a new snapshot from the current DOM. Continuous typing and single-character deletion at a collapsed caret merge by updating only the final snapshot. Range replacements and selected deletions always start a new transaction; subsequent contiguous character edits of the same type can continue it. Paste, drop, and composition commits remain standalone transactions. There is no time-based grouping heuristic.

This selection rule is deliberate. Local macOS comparisons found that Chrome's native deletion undo creates a selection over restored text, whereas Firefox restores the pre-deletion caret. The controller follows the latter, consistent before/after model rather than accumulating deleted ranges in changing grapheme coordinates. Both tested browsers restore a replacement's original backward selection and keep redo independent of later navigation.

Selection changes observed through `select` and `selectionchange` also end a group when they leave its expected caret. Selection events generated by rendering at that caret do not split contiguous typing. Undo/redo always ends the open group and clears pending native-edit metadata. During composition, history requests leave the draft and committed history untouched, and keyboard shortcuts remain available to the IME. A successful composition commit becomes one transaction.

Only a value-changing edit discards the redo branch. No-op/rejected edits, accepting the current controlled value, updating the reset value, and toggling reveal preserve it. Assigning a different `secretValue` or resetting the form clears both stacks. Readonly and disabled inputs do not consume entries. History restoration uses recorded values even if `maxlength` has since changed. Empty-stack requests restore the authoritative presentation without emitting `input`. A successful traversal emits one `input` with its history input type and null data, after all state changes, so callbacks can safely edit again. Blur emits `change` only when user editing left the secret different from the focus/reset baseline.

Snapshots retain full strings rather than edit deltas. This keeps restoration independent of later Unicode segmentation or DOM mutations and suits short secret fields. History has no fixed depth limit; its memory use grows with retained transactions, and reset or a different programmatic value releases both branches. Avoid adding a generic editor framework or per-browser history policy without a concrete requirement.

The native context menu may still disable Undo or Redo because Web content cannot register entries in the input's private undo manager. Do not use deprecated `execCommand()` or allow plaintext DOM edits merely to populate that stack. Exact transaction boundaries and restored selections also vary by browser and operating system; the controller approximates their shared behavior rather than claiming identical native history.

Concealed native password fields do not export their selection in all target engines. While redacted, cancel copy, cut, and selection dragging rather than putting either the secret or misleading bullets on the clipboard. Revealed mode deliberately restores native copy, cut, and drag behavior. Paste and external drop remain supported in both states. Their data may be absent from `beforeinput`; capture it from the preceding transfer event and consume it once. Pending transfer data and non-cancelable edit metadata expire at the next microtask checkpoint so unrelated input cannot reuse them.

Ordinary caret, range selection, keyboard, and pointer handling stay native. Consequently, character-wise operations line up with one mask per grapheme, but word-wise movement and pointer word selection see a run of bullets instead of the secret's undisclosed word boundaries. Do not replace the native editor merely to close that gap.

Autofill commonly mutates the DOM without a cancelable `beforeinput`. The controller never adopts that value and restores the authoritative presentation—masks while redacted, the actual secret while revealed—on the next observed input/change/edit event. Direct script writes without events cannot be observed immediately because value property changes do not produce mutations or events.

`mask()` also sets `autocomplete="off"` and the known field-level opt-out hints for 1Password, Bitwarden, Dashlane, LastPass, and Proton Pass. The React and Vue adapters render the same attributes before their controller attaches. These vendor contracts are best-effort and can change or be ignored; they reduce third-party UI and writes but do not replace the authoritative-state boundary.

Autocorrection and browser-managed `insertReplacementText` are intentionally rejected because they are not reliably distinguishable from autofill. The controller enforces `autocomplete="off"` and defaults autocapitalization, autocorrection, and spellcheck to off unless the author explicitly configures those text services.
